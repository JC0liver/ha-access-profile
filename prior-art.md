# Prior art: Access profile for HACS integrations

2026-11-19. Read-only research for `proposal.md` (sections 4–5). Every item has a source URL. "Unverified" means I couldn't read the primary source.

## Verdict

1. **Not for HA.** Neither OHF nor HACS publishes per-release security data. In March 2026 HACS said it "does not perform security assessments, code audits, or vulnerability reviews". The only existing tools are a few small community scanners that run on the user's own instance.
2. **Closest outside model: Obsidian Community** (May 2026). Its plugins also run unsandboxed and in-process. It scans every version automatically, shows a scorecard on each plugin page, pulls failing versions from search within 24 h, and plans per-plugin capability disclosures.
3. **Closest model for the check engine: Grafana `plugin-validator`.** It runs Semgrep code rules, a ClamAV scan, an LLM review and OSV, and it diffs the release archive against the source repo. That diff is the same check as our "release zip differs from tagged source" gate.

### Wording precedents (verbatim)

- npm: "it does not guarantee the package has no malicious code"
- OpenSSF: "The checks themselves are heuristics; there are false positives and false negatives."
- Obsidian: "Scorecards are new and can contain errors"
- Google Play: "This review does not verify the accuracy and completeness of the developer's … disclosure"
- WordPress: "This plugin checker is not perfect, and never will be."
- HACS (today): "everything inside HACS including HACS itself is custom and untested by Home Assistant"
- ha-security-monitor: "It helps you spot problems; it does not make your installation secure on its own."
- Counter-example, Homebridge: "reviewed and endorsed by the Homebridge project team"

## What we should borrow or avoid

- **Borrow Obsidian's flow:** automated scan per version, block failing releases (from search or from update), manual review only for the gate queue, results on a per-plugin tab with word labels rather than a number. Plan the backfill of already-listed integrations up front, since Obsidian's grandfathering has no deadline.
- **Borrow Grafana's engine shape:** Semgrep code rules, AV, OSV and a source-vs-archive diff. The diff closes our `zip_release` blind spot. Read haxsec's HA Semgrep rules before writing ours.
- **Gate updates that raise the level,** as Chrome disables an extension until the user accepts new warnings. It's a proven pattern for open question 3.
- **Avoid an aggregate number or a publisher badge.** OpenSSF's own docs say aggregates tell you nothing about behaviour, and VS Code's domain check is commonly misread as a code check. Homebridge "Verified" is an explicit endorsement.
- **Footer wording:** model it on npm's "does not guarantee … no malicious code" plus Obsidian's "can contain errors". Suggested: "Automated check of this release. It can miss things and can be wrong. Not a security review by the Open Home Foundation."
- **Show author explanations as unverified,** like Google Play's "does not verify the accuracy" note, so they never read as OHF agreeing.
